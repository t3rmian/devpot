最近の*log4j2*のゼロデイ脆弱性は、Java界で大きな騒ぎになりました。
確かに、ソフトウェア企業は自社製品で使用している依存関係にもっと関心を持つようになりました。
現在、*log4j*には2.17.1と2.17.2という2つの安全なバージョンがあります。
しかし、一部のレガシー製品では、2015年にEOL（End Of Life）を迎えた*log4j*のバージョン1.2がまだ使用されています。さらに、*slf4j*ファサードさえ使用していないケースもあります。

セキュリティパッチの適用プロセスでは、1.2を、重大なバグが修正された同じクラスを含む*reload4j*ライブラリに置き換えることを選択できます。しかし、最も推奨されるアプローチは、*log4j2*に完全に移行することです。
3番目の選択肢は、中間的な方法として、バージョン2のコアに接続する古いAPIを公開する*log4j-1.2-api*ブリッジを使用することです。

APIとは別に、*log4j2*は[2.13.3](https://issues.apache.org/jira/browse/LOG4J2-63)という早い段階で古い設定のサポートを導入しました。
ただし、すべての設定項目が完全にサポートされていたわけではないので注意が必要です。特に、*apache-log4j-extras*のようなカスタムアペンダと組み合わせる場合はそうです（ちなみに、このライブラリは1.2のクラスのサブセットを含んでいるため、その使用はやや疑問視されます）。

> **注意:** 2.18では、[org.apache.log4j.<wbr>rolling.RollingFileAppender](https://issues.apache.org/jira/projects/LOG4J2/issues/LOG4J2-3483)のような*apache-extras*のより多くの設定要素をサポートするための有望な機能強化が導入される予定です。

これを念頭に置いて、設定をアップグレードするか、完全にサポートされていれば古いものを再利用することを期待できます。
注目すべき点として、2.17.1と比較して[2.17.2](https://logging.apache.org/log4j/2.x/changes-report.html#a2.17.2)で実装された機能強化があります。
以前は、ブリッジを介してプログラム的に設定をロードする方法はno-op（何もしない操作）でした。2.17.2では、多数の修正に加えて、この動作も変更されています。

もし1.2 APIを使用して設定をロードするコードがまだ残っている場合、例えば次のようなものです。
```java
DOMConfigurator.configure(filename);
DOMConfigurator.configureAndWatch(configFilename, delay);
```
残念なエラーに遭遇する可能性があります。[移行ドキュメント](https://logging.apache.org/log4j/2.x/manual/migration.html)で言及されているように、これは許可されていませんが、
2.17.1までは悪影響はありませんでした。
2.17.2では、1.xの設定をロードしようと試みるため、このインターフェースを使用している場合、アップグレードのアプローチに影響します。
```java
public class DOMConfigurator {
    //2.17.1:
    public static void configureAndWatch(final String configFilename, final long delay) {
    }

    //2.17.2:
    public static void configureAndWatch(final String fileName, final long delay) {
        XMLWatchdog xdog = new XMLWatchdog(fileName);
        xdog.setDelay(delay);
        xdog.start();
    }
    //...
}
```
システムプロパティに関しては、ブリッジを使用する場合、*log4j2*で知られている`log4j.configurationFile`プロパティが設定の優先ソースとなります。
レガシーの1.x `log4j.configuration`プロパティを同時に使用して、新しい形式にスムーズに移行できます。
